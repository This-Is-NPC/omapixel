# Adding a language

Every word the program says comes from a JSON file in `i18n/`. Adding a language
is copying one file, translating the right-hand sides, and putting it where the
program looks. Nothing is compiled and nothing is regenerated.

```bash
cp i18n/en.json i18n/pt.json
$EDITOR i18n/pt.json
omapixel i18n pt          # what is still missing
OMAPIXEL_LANG=pt omapixel-studio drawing.json
```

## The file

```json
{
  "menu.file": "File",
  "menu.open": "Open…",
  "panel.palette.slots": "%1 slots",
  "status.frames": "%1 · %2 frames · %3 fps"
}
```

Keys on the left, never translated. Text on the right, always translated.
`%1`, `%2` and `%3` are filled in by the program, in that order. Keep them, and
move them if your language wants them elsewhere:

```json
  "status.frames": "%1 · %2 quadros a %3 fps"
```

`i18n/en.json` is the canonical list of every string the program can say, so it
is also the to-do list. Translating is going down it.

## Where the program looks

In this order, first hit wins:

| | |
|---|---|
| `~/.config/omapixel/i18n/` | yours: drop a file here and it is used, with no rebuild |
| `<checkout>/i18n/` | the ones that ship |
| `<binary>/../share/omapixel/i18n/` | an installed copy |

Which language, in this order: `OMAPIXEL_LANG` in the environment, then
`language` in [the config file](configuration.md), then the system's. The
environment first so one run can be in another language without editing
anything; the config file is where a lasting choice belongs.

`pt_BR` is tried whole and then as `pt`, so one Portuguese catalogue serves a
Brazilian system until somebody writes a Brazilian one.

## What happens when a translation is thin

English is loaded first and the chosen language on top of it, so a half-finished
catalogue shows English where it is thin rather than gaps. A key that exists in
no catalogue shows as the key itself: visible, and obviously wrong, which is
what you want a mistake to look like.

That means you can ship a translation of twenty strings and it works.

## Keeping up with the program

```bash
omapixel i18n            # every catalogue, and how far along each is
omapixel i18n pt         # what pt.json is missing, and what it no longer needs
```

It lists keys added since the translation was written, and keys the program has
stopped asking for. It exits non-zero when either list is non-empty, so it can
be a step in a pipeline. `mise run i18n pt` is the same thing.

Two tests in the suite hold the code and `en.json` together. One reads every
`T.t("…")` in the QML and fails if the English catalogue has no string for it.
The other is the one that matters more: it fails on any English sentence written
*into* the QML instead of asked for by key. A string that never asked is
invisible to the first test, and six of them had quietly stayed in English
through the whole change, which is the sort of thing a translator finds and
nobody else does.

## Why not Qt's own translations

Qt has `.ts` files, `lupdate` and `lrelease`. They are more capable, with plural
forms, context and disambiguation, and they end in a binary `.qm` nobody can
read or edit without the toolchain. The ask here was a file a person can copy,
translate and drop in. If plural forms become a real problem, the honest answer
is to add a second key rather than a second toolchain: `status.frames` and
`status.oneFrame` already work that way.
